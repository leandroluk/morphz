# Spec: Release Readiness

## Summary

Turn the repo from "code-complete per INSIGHT.md" into a project that can
actually cut a real `v0.1.0` release with zero manual steps beyond pushing
one git tag. `release-pipeline` already built the publish plumbing
(`.github/workflows/release.yml` — npm + VSCode Marketplace + Open VSX,
tag-triggered, version-from-tag). This feature closes the gaps that make
that pipeline unsafe/incomplete to run today: missing package-facing
docs, missing LICENSE files, no generated CHANGELOG, no GitHub Release,
no npm provenance, and no `npm pack` verification of the `./ts-plugin`
subpath export.

Extends `[[release-pipeline]]`. Does NOT replace its trigger model: tag
push stays the release action; version stays derived from the tag.
Changelog is generated from Conventional Commits (already enforced repo-
wide via commitlint + lefthook) using **git-cliff**, chosen over
semantic-release (bad monorepo story, no human gate on version pre-1.0)
and release-please (more moving parts; noted as the post-1.0 upgrade
path).

## Requirements

### Package-facing docs & legal

- REQ-001: `packages/core/README.md` exists and is included in the npm
  tarball (npm auto-includes a package-root `README.md`). Content: what
  `morphz` is, install, a minimal `Struct` + `Define` example, links to
  the repo. Derived from `INSIGHT.md` §1–8, not invented.
- REQ-002: A `LICENSE` file (MIT, `Copyright (c) 2026 Leandro Santiago
Gomes`) exists at repo root AND is shipped inside every published
  artifact: `packages/core` npm tarball and `packages/vscode` `.vsix`.
  `packages/core/package.json` / `packages/vscode/package.json` already
  declare `"license": "MIT"`; the files must back that claim.
- REQ-003: Repo-root `README.md` exists — the GitHub landing page:
  one-paragraph pitch, package table (`morphz`, `morphz-vscode`,
  internal `ts-plugin`), monorepo layout, dev/build/test commands, a
  "Releasing" section pointing at `.github/workflows/`.

### Changelog

- REQ-004: `git-cliff` config (`cliff.toml`) at repo root, grouping
  Conventional Commit types into changelog sections (Features, Bug Fixes,
  Documentation, etc.), skipping `chore`/`style`/`ci`-only noise.
- REQ-005: `CHANGELOG.md` at repo root, in Keep a Changelog-compatible
  layout, generated by git-cliff. First entry is `0.1.0` covering the
  whole history to date (v1–v4 batches) — generated from commits, then
  committed.
- REQ-006: `release.yml` regenerates `CHANGELOG.md` for the pushed tag's
  range during the release run and uses that rendered section as the
  GitHub Release body. The regenerated file is either committed back to
  `main` or attached to the Release (decided in Design) — no hand-editing
  of `CHANGELOG.md` in the normal flow.

### Pipeline hardening (all in `.github/workflows/release.yml`)

- REQ-007: `npm publish` runs with `--provenance`; the `publish-npm` job
  has `permissions: id-token: write` (and `contents: read`). Publishing
  `0.1.0` this way makes it the npm `latest`, superseding the existing
  `0.0.1-alpha.0` that currently holds both `latest` and `alpha`
  dist-tags.
- REQ-008: A `build-test` step runs `npm pack` (dry-run or real) for
  `packages/core` and asserts the tarball contains `README.md`,
  `LICENSE`, and a non-empty `dist/ts-plugin/` (`index.cjs` +
  `index.d.ts`) — the `./ts-plugin` export subpath must not ship broken.
  Fail the job if any is absent.
- REQ-009: After all three `publish-*` jobs succeed, a `github-release`
  job creates a GitHub Release for the tag: title = the version, body =
  the git-cliff-rendered section for that tag, with the built `.vsix`
  attached as a release asset. Needs `permissions: contents: write`.
- REQ-010: `vsce package` step verifies the `.vsix` contains the readme
  (`extension/readme.md` — vsce lowercases it) and the license
  (`extension/LICENSE.txt` — vsce renames `LICENSE`), and does NOT
  contain `src/**` or any `*.map`. NOTE: `.vscodeignore` originally only
  had top-level `*.map`; `dist/extension.js.map` leaked — fixed by adding
  `**/*.map` (SPEC_DEVIATION, recorded in STATE.md).

### Verification (no secrets required)

- REQ-011: Everything except the actual `publish` / `gh release` network
  calls is verifiable locally / in CI without real tokens: `git-cliff`
  render, `npm pack` + tarball inspection, `vsce package` + `.vsix`
  inspection, `actionlint` (or structural YAML parse if unavailable) on
  the workflow.

## Out of Scope

- Creating npm / Azure DevOps / Open VSX accounts or the `NPM_TOKEN` /
  `VSCE_PAT` / `OVSX_PAT` repo secrets — user's action. Pipeline stays
  un-exercised end-to-end until those exist (documented limitation,
  carried from `[[release-pipeline]]`).
- semantic-release / release-please / changesets adoption — evaluated and
  rejected for now; release-please noted as the post-1.0 revisit.
- Auto-bumping `package.json` versions outside the tag flow — version
  stays tag-derived (REQ-006 of `[[release-pipeline]]`).
- A VSCode extension `icon`, marketplace banner theme, `keywords` tuning,
  npm `keywords` tuning — cosmetic, separate pass.
- `docs/` root directory — still deferred per user.
- Trimming sourcemaps from the npm tarball — deliberate no-op.

## Open Questions

- OQ-1 (for Design): does the release run **commit** the regenerated
  `CHANGELOG.md` back to `main` (needs `contents: write` + a bot push on
  a tag build, which is slightly awkward), or is the committed
  `CHANGELOG.md` updated by the human just before tagging and CI only
  _renders_ the section for the Release body (no write-back)? Leaning
  toward: human runs `pnpm changelog` before tagging (updates the file in
  the same commit that bumps nothing — the tag is on that commit); CI
  only renders `--latest` for the Release body. Simpler, no bot push.
- OQ-2 (for Design): `git-cliff` as a root devDependency + `pnpm dlx`, or
  pin via the `orhun/git-cliff-action` in CI and a local `pnpm` script
  wrapper? Both, probably: action in CI, devDep for local `pnpm changelog`.
- OQ-3: first tag literally `v0.1.0` on the current `main` HEAD, or cut a
  short-lived `release/0.1.0` branch first? Solo repo, linear history —
  tag HEAD directly unless Design surfaces a reason not to.
